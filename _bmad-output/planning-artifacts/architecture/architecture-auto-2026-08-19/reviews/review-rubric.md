# Rubric Review — [Proyecto Auto] Architecture Spine

## Overall verdict

The spine is mostly solid: its ten ADs fix real, well-scoped divergence points (Clean Architecture boundary, the Angular/Flutter split, token drift, auth delegation, comparison ownership/cap/snapshot rules, geography-as-data), the tech stack is verified-current per the decision log, and the deployment topology is decided rather than silent. However, two decisions that were actually made in the coaching conversation (`.memlog.md`) did not survive into the spine as enforceable ADs — the backoffice's architecture (including its auth model) and the SMS-OTP-in-MVP question — and one PRD NFR (search/filter performance, NFR-2) received zero architectural treatment despite standing in direct tension with a stack choice (Container Apps scale-to-zero). AD-8's DB-level enforcement mechanism is also underspecified in a way that a plain CHECK constraint cannot actually satisfy. These are fixable gaps, not a wholesale rewrite.

## Findings

- **critical** FR-14 backoffice architecture is dropped from the spine. `.memlog.md` records a real decision — "sección admin gated por rol dentro de la misma app Angular (no app separada)" — but the spine never states this. The only mention is in the backend source tree ("role-gated backoffice (FR-14) as a section of this same API/app"), which describes the *API* layer, not where the admin UI lives. Nothing says whether staff/admin accounts use the same passwordless OTP flow as AD-4 (customers) or a separate credential model, and no Role/Permission concept appears on the `USER` entity in the ERD. Two teams building independently could easily diverge: one building a separate admin app, another assuming shared OTP login for staff. (ARCHITECTURE-SPINE.md — AD-2, Structural Seed → Backend source tree, ERD). *Fix:* Add an AD stating the backoffice lives inside the same Angular codebase as a role-gated section (not a separate app/deployment), and specify the staff auth model (reuse AD-4's OTP, or name a separate mechanism) plus how role/permission is represented on `USER`.

- **high** SMS OTP's MVP status is left open in a way that contradicts EXPERIENCE.md. The Deferred section says "whether SMS ships in the MVP or is added after launch is open." But EXPERIENCE.md's Flujo 2 depicts Diego signing up with a phone number and receiving a one-time SMS code as a confirmed, first-class MVP flow (not marked speculative), and PRD FR-15 lists "email o teléfono" as account identifiers on equal footing. If SMS genuinely isn't decided for MVP, the UX spec's phone-signup flow cannot be built as written — leaving mobile/frontend teams free to build phone-OTP UI while the backend never wires the SMS channel. (ARCHITECTURE-SPINE.md — Deferred; contradicts EXPERIENCE.md Flujo 2, PRD FR-15). *Fix:* Resolve this as an AD, not a Deferred item: either commit SMS to MVP (aligning with EXPERIENCE.md), or state explicitly that phone-identified accounts still receive their OTP via email in MVP (and get EXPERIENCE.md's Flujo 2 amended). Leaving it open lets two units diverge, which is exactly what Deferred should not permit.

- **high** NFR-2 (search/filter results in <2s) has no architectural treatment at all — not decided, not deferred, not flagged as an open question. There is no mention of indexing strategy, caching, or query design for `Agency`/`Vehicle` filtering across up to 7 filter dimensions (FR-4–FR-9). Worse, it sits in unaddressed tension with the chosen Azure Container Apps **consumption plan (scale-to-zero)**: cold starts after idle periods are a well-known latency cost that could blow the 2s budget on the first request after a scale-to-zero event, and the spine never reconciles the two. (ARCHITECTURE-SPINE.md — Stack, Deferred; PRD NFR-2). *Fix:* Either add an AD/Deferred entry naming the performance approach (indexing on filter columns, minimum instance count vs. scale-to-zero trade-off, or caching), or explicitly flag the scale-to-zero/NFR-2 tension as an open question for implementation to resolve.

- **medium** AD-8's "DB-level constraint/check" for the 3-vehicle comparison cap is not literally achievable with a plain SQL `CHECK` constraint, since `CHECK` cannot aggregate/count sibling rows. As written, two independent implementers could diverge on *how* to satisfy the rule — one adds a trigger, another interprets "constraint/check" loosely and skips DB-level enforcement entirely, believing API validation already covers it. (ARCHITECTURE-SPINE.md — AD-8). *Fix:* Name the actual mechanism, e.g. a `slot` column (1–3) on `COMPARISON_VEHICLE` with `CHECK (slot BETWEEN 1 AND 3)` plus a `UNIQUE (comparison_id, slot)` constraint, or an explicit trigger — so the rule is unambiguously implementable.

- **low** AD-4 specifies that clients only "request, store, and attach tokens" but doesn't set a floor for *how* tokens are stored (e.g., secure/keychain storage on Flutter vs. an XSS-safe pattern on Angular). Given both clients are independently built against the same JWT contract, this is a minor but real place two teams could diverge on security posture. (ARCHITECTURE-SPINE.md — AD-4). *Fix:* Add a one-line convention (e.g., "tokens are never persisted in a location readable by third-party JS/webviews — platform secure storage only") to the Consistency Conventions table, or explicitly defer it with a note.
