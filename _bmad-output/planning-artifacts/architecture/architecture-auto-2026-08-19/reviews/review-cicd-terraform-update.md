# CI/CD & Terraform Update Review — [Proyecto Auto] Architecture Spine

## Overall verdict

AD-17 and AD-18 are sound additions: both pass the two-independently-built-units-diverge test on their own terms (AD-17 names the "two developers diverge on how a deploy actually happens" failure explicitly; AD-18 names dev/staging/prod drift plus idle-cost bleed), their Rules are concrete enough to audit (named tool, named steps, named branch-protection behavior — more specific than several existing ADs), and they don't contradict AD-1–AD-16, including AD-12's Container Apps cold-start tension and the staging/prod-stability language, which the updated "Deployment & environments" prose correctly scopes as unaffected by dev's ephemerality. The new mermaid diagram is syntactically valid and consistent with the existing diagram's node-labeling style. The Stack table and Deferred-list edits are internally clean — no dangling reference to the old "CI/CD undecided" framing survives anywhere in the document (verified by full-text scan).

That said, four gaps are worth closing before this is load-bearing for implementation: one wording loophole in AD-17's own Rule, one asymmetry in the new diagram that could mislead a reader about which environments get destroyed, one unaddressed PR-preview-RG cost/concurrency question that cuts against AD-18's own stated cost rationale, and one genuine cross-AD seam — no word anywhere on seed/fixture data for a freshly-created (empty) dev database, which is exactly the kind of two-teams-diverge risk AD-13 (AGENCY_BRAND derivation) already exists to prevent, now newly live because dev no longer persists between sessions. None of these are blocking; all are same-shape fixes to the ADs/diagram that are already mostly right.

## Findings

- **medium** AD-17's Rule scopes the manual-deploy prohibition to "against a shared environment" ("No deploy step is ever performed by hand against a shared environment"), but AD-18's prose says dev resource-group lifecycle is "driven by AD-17's pipeline, not a developer's local CLI" — i.e., the no-manual-deploy floor is meant to apply to dev too, even though dev isn't "shared" in the sense AD-17's own wording uses. A team reading AD-17 in isolation could reasonably conclude that hand-running `terraform apply`/`az` CLI against *their own* ephemeral dev RG is fine, since it isn't "shared" — directly contradicting AD-18's explicit intent. (ARCHITECTURE-SPINE.md lines 143–144 vs. 230.) *Fix:* change AD-17's Rule to "against any environment, shared or ephemeral" (or add an explicit cross-reference to AD-18's dev clause), so the two ADs can't be read as disagreeing about whether local manual `terraform apply` to dev is permitted.

- **medium** The new "CI/CD & environment lifecycle" diagram's `Apply` node is explicitly scoped — `"terraform apply\n(dev: creates ephemeral RG)"` — but the terminal `Destroy` node carries no environment qualifier (`"terraform destroy\n(on demand / schedule)"`), even though the surrounding prose (line 216) and AD-18 both state staging/production resource groups are long-lived and never torn down. Read as a single linear pipeline, the diagram implies every environment that goes through `Apply`/`Deploy` also eventually hits `Destroy` — true for dev, false for staging/prod. (ARCHITECTURE-SPINE.md lines 220–228.) *Fix:* label `Destroy` symmetrically, e.g. `"terraform destroy\n(dev only — on demand/schedule)"`, or add a second branch/note showing staging/prod stop at `Deploy`/`Use` with no destroy edge.

- **medium** Neither the diagram nor AD-17/AD-18's text distinguishes a PR-triggered run (build/test/`plan`, no apply against anything persistent) from a push-to-`main`-triggered run (full `apply`/`deploy`). AD-18's prose that dev RGs are "named per-branch or per-session" reads as implying every open PR/branch gets its own live, billing resource group — which is in tension with AD-18's own stated purpose ("specifically to avoid standing dev-environment cost between sessions"): several concurrently open PRs would mean several concurrently live Postgres/Container Apps instances, not one. (ARCHITECTURE-SPINE.md line 144 "every push to `main` and every PR runs..."; line 230 "named per-branch or per-session.") *Fix:* either clarify that PR runs stop at `plan` (no RG created) and only a merge or explicit trigger creates a dev RG, or explicitly accept per-branch preview RGs and note a concurrency/cost cap — either is fine, but the spine should pick one rather than leave it inferable both ways.

- **medium** Genuine cross-AD seam, not a contradiction: AD-18 makes dev Postgres Flexible Server instances ephemeral (destroyed and recreated on demand), but nothing in the spine — not an AD, not a Deferred bullet — names what a freshly-created dev database contains. This matters specifically because of AD-13: `AGENCY_BRAND` is required to be "computed/materialized from actual `Vehicle` inventory... never a table a backoffice user edits directly." If two developers each improvise their own seed script for their own fresh dev RG — one inserting `Vehicle` rows only and trusting derivation, another hand-inserting `AGENCY_BRAND` rows to save time — their dev environments disagree on catalog state in exactly the way AD-13 exists to forbid in production. The same applies more mildly to AD-9 (freshness timestamps are meaningless to test against an empty or arbitrarily-seeded catalog) and to the weekly-curation workflow assumed everywhere else in the PRD, which has no analog in a from-empty dev RG. (Cf. ARCHITECTURE-SPINE.md AD-13 lines 116–120, AD-9 lines 92–96, Deferred list lines 264–277 — no seed/fixture bullet exists.) *Fix:* this doesn't need a full AD — a single Deferred-list bullet is enough, e.g. "Dev seed/fixture data for ephemeral resource groups — not designed here; a from-empty dev DB currently has no defined bootstrap, so ad hoc per-developer seeding could violate AD-13's derivation rule inside dev alone." That closes the seam at the correct altitude (named and flagged, not solved) instead of leaving it silently assumed away.

## Non-findings (checked, no issue)

- AD-12's Container Apps cold-start/min-replica discussion is scoped to NFR-2 (production search latency) and is unaffected by AD-18 — dev's ephemerality doesn't touch the scale-to-zero-vs-min-replica trade-off, which is a staging/prod concern only.
- Staging/production stability language (line 216, AD-18's "Staging/production resource groups are longer-lived") is consistent with, not contradicted by, "Dev is different by design" — the update correctly carves dev out rather than implying staging/prod are also ephemeral.
- Stack table additions (`GitHub Actions`, `Terraform`, lines 179–180) and the narrowed Deferred bullet ("Flutter's CI/CD pipeline specifics," line 267) are internally consistent; a full-text scan for "CI/CD," "deploy," "terraform," "manual," "portal," and "ClickOps" across the whole document turned up no stale claim that CI/CD "is not decided" anywhere outside AD-17/18's own scope.
- The new mermaid block (lines 220–228) is syntactically valid `flowchart LR` — quoted node labels with embedded `\n` match the style already used in the "Deployment & environments" diagram (e.g. `"Static Web Apps\n(Angular web)"`), and node IDs (`Push`, `CI`, `Plan`, `Apply`, `Deploy`, `Use`, `Destroy`) are unique within the block.

---

**Verdict:** Adopt as-is is acceptable; recommend folding in the four medium fixes above (all are wording/diagram-label tightenings plus one new Deferred bullet — no re-architecture) before treating AD-17/AD-18 as final for implementation.
